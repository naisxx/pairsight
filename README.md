# PairSight

PairSight is a web app with real user accounts, built on the 8x web template
stack. It runs and is demoed on **localhost**: a local Supabase (in Docker)
provides auth and Postgres, and there is no hosted Supabase, Vercel project, or
production deployment.

PairSight helps teams compare entity-resolution vendors: it uses Jev to judge
record pairs and shows where each vendor agrees or disagrees. See
[`docs/PairSight-Product-Overview.md`](docs/PairSight-Product-Overview.md) for
the product and [`docs/PairSight-V1-Scope.md`](docs/PairSight-V1-Scope.md) for
the v1 scope, domain rules and open questions.
[`docs/PairSight-Delivery-Plan.md`](docs/PairSight-Delivery-Plan.md) is the
implementation reference.

## Stack

| Layer           | Choice                                                        | Note                                                                                                                                                                               |
| --------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Framework       | Next.js 16 (App Router, Turbopack, React Compiler) + React 19 | See `AGENTS.md` for the v13/14→16 breaking changes that matter                                                                                                                     |
| Styling         | Tailwind CSS v4 (CSS-first, no `tailwind.config.js`)          | Tokens in `src/app/globals.css`, see `DESIGN.md`                                                                                                                                   |
| Database        | Prisma 6                                                      | Schema-only workflow: migrations are generated from the schema diff and committed, never hand-written. Prisma 7 is a deliberate future upgrade (driver-adapter migration required) |
| Auth            | Supabase Auth                                                 | Auth/session only — Prisma still owns all application data. Removed entirely for landing pages with no accounts, see `docs/rules/auth.md`                                          |
| Server state    | TanStack Query                                                | `QueryClient` created inside `useState`, never module scope                                                                                                                        |
| i18n            | next-intl                                                     | Component-scoped translation files                                                                                                                                                 |
| Observability   | Sentry + PostHog                                              | Both no-op gracefully until real keys are set; unified behind `captureError`/`captureClientError`, see `docs/rules/error-handling.md`                                              |
| Testing         | `node --test` (unit) + Playwright (e2e)                       |                                                                                                                                                                                    |
| Package manager | pnpm                                                          | Version pinned in `package.json`                                                                                                                                                   |

## Setup (localhost)

Prerequisites: Node `>=22.18` (CI runs 22), pnpm 10.6.2 (`corepack enable`),
Docker Desktop running.

```bash
pnpm install              # also installs the git hooks + generates the Prisma client
pnpm supabase start       # local Supabase in Docker (first run pulls images)
pnpm supabase status      # prints the local URLs and keys used below
```

Create two gitignored env files:

- **`.env`** holds only `DATABASE_URL` and `DIRECT_URL`, both set to the
  `DB_URL` from `pnpm supabase status` (port **54322**, no pooler locally).
  It's `.env`, not `.env.local`, because the Prisma CLI reads only `.env`.
  Next.js reads it too, and `db:run-once`/`check:rls` load it with
  `--env-file-if-exists`.
- **`.env.local`** is a copy of `.env.example` without the two database
  lines, with `NEXT_PUBLIC_SUPABASE_URL="http://127.0.0.1:54321"`,
  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` = `PUBLISHABLE_KEY`,
  `SUPABASE_SECRET_KEY` = `SECRET_KEY`, and any `CRON_SECRET`
  (`openssl rand -hex 32`).

```bash
pnpm exec prisma migrate deploy   # apply the committed migrations — never `migrate dev`
pnpm db:run-once                  # apply prisma/run-once.sql if this database hasn't had it
pnpm demo:seed                    # load the read-only /sandbox evaluation (safe to rerun)
pnpm dev
```

Open http://localhost:3000. English is served unprefixed, and `/en`
redirects back to `/`. Sentry and PostHog do nothing until their keys are
set, and nothing needs them to run. Supabase Studio is at
http://127.0.0.1:54323 and caught auth emails at http://127.0.0.1:54324.
`pnpm supabase stop` shuts the containers down and keeps the data.

**Jev (TypeSafe).** Live evaluations need `TYPESAFE_API_KEY` in `.env.local`;
without it, a run stops with a clear configuration error. With the key set,
`pnpm jev:check` runs a small live check on fictional pairs (response shape,
pinned model, latency, repeatability, 429s) and records each call in
`ai_usage`. To develop without a key, run `pnpm jev:stub` and start the app
with `TYPESAFE_API_BASE_URL=http://127.0.0.1:4010/v1` and any
`TYPESAFE_API_KEY`. The stub is a deterministic toy, not Jev, and reports
its model as `jev-stub`. Use fictional or anonymized records only.

## Environment variables

Every variable the app reads is documented inline in `.env.example` (what
it's for, its fallback behavior, how to generate it) and validated at boot
by `src/lib/env.ts` — a misconfigured deployment fails immediately with a
clear message instead of an obscure error three requests later. Groups:
database (Prisma), Supabase Auth, Sentry, PostHog, Slack alerting, i18n,
cron secret, app URL. `pnpm check:env` fails if any `process.env.X` in `src/` is missing
from either `.env.example` or the schema. Locally the database URLs live in
`.env` and everything else in `.env.local` — see Setup above.

## Database & migrations

Prisma schema (`prisma/schema/*.prisma`, one file per domain area) is the
only thing you hand-edit. **The generator writes the migration, you write
the schema** — never touch a file under `prisma/schema/migrations/` yourself.
The one SQL file you do hand-write is `prisma/run-once.sql`: a one-off
change that isn't a schema change (fix a value, insert reference rows,
replace a view). CI applies it to a throwaway database on every PR, and
`pnpm db:run-once` applies it locally; a ledger keyed by content hash makes
sure it never runs twice on the same database. Replace its content for the next
one-off.

PairSight generates migrations locally with the same generator CI uses:
edit the schema, then run `pnpm prisma:migrate:generate:check` (preview) and
`pnpm prisma:migrate:generate <name>`, which writes the migration and applies
it to your local database. Commit it with the schema change; CI's
`migrations` job re-checks it on the PR. Never `prisma db push` or
`prisma migrate dev`. The only migrations written by hand
are the documented exceptions: `ENABLE ROW LEVEL SECURITY` for each new table,
and data-preserving SQL when the generator refuses a destructive change. Full workflow, the
destructive-change safety net, and why this approach was chosen over the
org's other migration patterns: `docs/rules/migrations.md`.

## Auth

PairSight has user accounts, so it keeps Supabase Auth. It's already wired up
in `src/proxy.ts` (session refresh) and `src/lib/supabase/` (auth-only server
clients). Locally it runs against the Supabase started by
`pnpm supabase start`. It handles auth and sessions only: Prisma owns every
byte of application data, and `User.id` is the Supabase auth user's UUID. The
Data API is off in `supabase/config.toml`, and every table has RLS enabled with
no policies. See `docs/rules/auth.md` and `docs/rules/authorization.md`.

## Testing

```bash
pnpm test        # node --test over scripts/*.test.mjs and src/**/*.test.mts — fast, no browser
pnpm test:e2e     # Playwright — boots the app itself unless E2E_BASE_URL is set
E2E_PAIRSIGHT=1 pnpm test:e2e   # + the PairSight flow specs (needs local Supabase; starts the Jev stub)
```

`e2e/public.spec.ts` covers the signed-out surface (landing, auth, 404,
theme, accessibility) and needs no database, so it's what CI's e2e job runs.
The PairSight and sandbox specs (`e2e/pairsight.spec.ts`,
`e2e/sandbox.spec.ts`) need local Supabase; they run against `pnpm jev:stub`,
a local stand-in for TypeSafe's API, so they need no key. CI has no database,
so it skips them.

The `e2e-review` skill runs the e2e suite and reviews failures against
their actual trace/screenshot rather than guessing from the error message.

## Rules live in AGENTS.md, not CLAUDE.md

`AGENTS.md` is a short index into `docs/rules/*.md` — one topic-scoped
file per rule: database access, migrations, auth, AI usage tracking, state
management, code style, code quality, feature approach, commits, pull
requests, deployment.
`AGENTS.md` is the file every coding agent reads (Claude, Codex, Cursor,
...), not just Claude Code, and the individual files are plain markdown
any of them can open directly. `CLAUDE.md` is deliberately thin: it
`@`-includes `AGENTS.md` and holds only the two things that are genuinely
Claude-Code-specific (session-log tracking, the skills list). Add new
rules under `docs/rules/` and link them from `AGENTS.md`; don't grow
`CLAUDE.md` back into a dumping ground.

`DESIGN.md` has the design-token/component conventions — read it before
styling anything. It ships a neutral starter token set (light + dark, via
`prefers-color-scheme`), not a real brand identity; that comes later, from
an actual mockup, via the org's `impeccable` tooling.

## Don't over-commit

Every push triggers a real, paid CI run. Don't commit after every small
step while iterating — run `local-review` locally first, then commit once
the work is actually done, not once per fix as you go. One feature commit,
plus at most one consolidated fix commit if something surfaces while
stabilizing it — not a string of "fix", "actually fix", "fix for real"
commits that each burn a CI run before anyone's looked at the last one.
Full rule, with the reasoning: `docs/rules/commits.md`.

Same principle applies to the PR itself: if you need to open one before
the work is done, open it as a **draft** with a placeholder title — don't
write a final-sounding description for work that isn't final. Write the
real title/description once, when the work is actually done, and mark it
ready for review at the same time. See `docs/rules/pull-requests.md`.

## Deployment

PairSight runs and is demoed on localhost only. There's no Vercel project, no
hosted Supabase and no production deployment. Never run a manual deploy
command (`docs/rules/deployment.md`).

GitHub CI still runs on every PR: gates, e2e, and the migrations job. Since
migrations are generated locally and committed, that job finds nothing to
generate and acts as a check (replay, drift, RLS). So no migrations token is
configured. If a PR ever reaches CI with a schema change but no migration,
CI would generate and push one using `GITHUB_TOKEN`, and that commit's run
would wait in `action_required`. Generate it locally instead.

There's no production database (`PRODUCTION_DATABASE_URL` is deliberately
unset), so `deploy-migrations.yml` fails on pushes to `main`. That's
expected here.

## Before you change anything

Read `AGENTS.md`, `DESIGN.md`, and `docs/rules/*.md`: the migration workflow,
the Server/Client Component rules, and the token conventions aren't style
preferences, they're enforced in CI (or, where noted, by `local-review`'s
manual pass). The stack choices are settled: TanStack Query for server state
and no global store, next-intl, Tailwind v4, Prisma 6.

What's built, what's next and what's deferred is the roadmap in
[`docs/PairSight-Delivery-Plan.md`](docs/PairSight-Delivery-Plan.md).
