## What PairSight is

**Who it's for:** a business choosing between entity-resolution vendors, for example before a CRM migration. Each vendor claims to find duplicate customer records, but raw match counts can't show who is more accurate. PairSight gives an independent, consistent second opinion on the same records, so the team can see where each vendor over-matches or misses duplicates, with far less manual review.

**What users provide:**
- The original records file, with a unique reference per record, and a mapping of its fields.
- Each vendor's export, as pairs or groups that point back to those references.
- A definition of "same entity": in v1, the same individual, not the same household.

The original file is essential. Without it, PairSight could never find duplicates that a vendor missed.

**How the pieces work together:**
1. **Blocking rules** (shared email, shared phone, surname plus postcode…) group records into overlapping buckets. They only nominate pairs worth checking; they never declare a match.
2. **The comparison set** is every pair from any bucket plus every pair any vendor matched, even pairs no blocking rule would find. Duplicates and reversed pairs count once, and self-pairs are dropped.
3. **Jev** judges each unique pair once, using the record fields and the identity definition. It never sees vendor names, scores or decisions. The same judgment is reused for every vendor.
4. **Our threshold** turns Jev's output into a PairSight decision: match or no match.
5. **The comparator** puts each successfully evaluated pair into one of four categories per vendor: both matched, PairSight only, vendor only, or neither matched. Pending and failed pairs stay visibly incomplete, never treated as nonmatches.

**Our app versus Jev:** the app does everything except judging a single pair: accounts, uploads, validation, mapping, the identity definition, blocking, building the pair set, calling Jev, tracking each pair's status, the threshold, the comparison and pair inspection. Jev does only the pair judgment.

**What results mean, and their limits:**
- The categories measure agreement, not correctness. "Vendor only" could be a vendor error or a PairSight error.
- Everything applies only to the evaluated set. Duplicates hidden in pairs that blocking excluded stay unseen, so a missed duplicate there never shows up.
- Jev is an AI judge and can be wrong, so any precision, recall or F1 figures would be AI estimates for the evaluated set only.

## 2. Architecture

**Layers**, reusing existing conventions:

| Layer | Location | Contents |
|---|---|---|
| Pure domain logic (unit-tested, no I/O) | `src/server/pairsight/` | `csv.ts` (parse and validate), `normalize.ts`, `blocking.ts`, `pairs.ts` (canonical order, dedupe, group expansion, union), `limits.ts`, `decisions.ts` (threshold and categories), `judgment.ts` (Jev request builder, response parser, config key) |
| Data access, always owner-scoped | `src/server/pairsight/store.ts` | Every function takes `ownerId`. Another user's evaluation returns 404, not 403. |
| Run engine | `src/server/pairsight/run-engine.ts` | Claims pending assessments and calls Jev (details below) |
| Jev provider | `src/server/ai/typesafe.ts` | The only file that calls TypeSafe; wrapped in `trackAiCall` like `anthropic.ts` |
| Auth | `src/server/auth/session.ts` | `requireUser()`: Supabase session, then `provisionUser`, then the `User` row |
| Mutations | server actions via `validatedAction` | Zod input, `AppError` for user-caused failures |

**AI tracking:**
- Add provider `typesafe` with a usage extractor for `{input_tokens, output_tokens}`.
- Record feature `pairsight_pair_judgment`, with `meta` holding ids only.
- The pricing gap from the scope doc (TypeSafe's output type isn't in the rate card) gets resolved in Milestone 1.

**How runs execute: a client-driven loop over work claimed in the database.** Starting a run freezes a snapshot and creates the pairs and pending assessments. The run page then repeatedly calls `advanceRun`, which:
- claims a batch of 10 pending assessments, plus any "running" ones older than 60 seconds (reclaimed after a crash or hot reload)
- calls Jev with concurrency 4 and a 20-second timeout
- retries 429, 529, timeouts and network errors up to 3 times with backoff
- marks 422 and unparseable responses as `failed` straight away
- treats 401 as a configuration error that stops the whole run
- returns progress counts

Closing the page pauses the run; reopening resumes it. "Retry failed" resets failed pairs to pending.

*Tradeoff:* a background worker would keep running without the page open, but `after()` only lasts the route's maximum duration, and a queue is infrastructure we don't need on localhost. The loop is simple, resumable and easy to test. A worker is a later extension.

**Data model** (new file `prisma/schema/pairsight.prisma`; every table gets an RLS migration):

| Model | Key fields |
|---|---|
| `Evaluation` | `ownerId?` (null for the demo), `name`, `kind` (live or demo); draft configuration: `identitySame`, `identityDifferent`, `countryCode`, `jevFields[]`, `blockingRules` (JSON), `threshold` |
| `SourceDataset` | `evaluationId`, `fileName`, `rowCount`, `referenceColumn`, `columnRoles` (JSON). Immutable: replacing the file creates a new dataset. |
| `SourceRecord` | `datasetId`, `reference` (unique per dataset), `rowNumber`, `values` (JSON, original values) |
| `VendorExport` | `evaluationId`, `datasetId`, `name`, `format` (pair, later group), `mapping`, `confirmedCompleteAt`, `pairCount` |
| `VendorMatch` | `exportId`, `recordAId`, `recordBId` (canonical order, unique) |
| `Run` | `evaluationId`, `datasetId`, `number`, `origin` (live or prepared), `status`, plus a **frozen snapshot**: the identity definition, `jevFields`, country, blocking rules, `exportIds[]`, `judgmentKey`, requested model, `threshold` |

## 3. v1 choices

| Topic | Choice |
|---|---|
| **Source CSV** | UTF-8, BOM allowed, header row, comma-delimited, ≤ 1 MB, ≤ 500 rows. Empty cell = missing. Trimmed reference, required and unique; errors list the row numbers. |
| **Vendor formats** | Standard pair CSV first: the user picks the "record A" and "record B" columns, and other columns (vendor scores) are ignored and never sent to Jev. Self-pair rows are skipped with a count, and duplicate or reversed rows collapse. Standard group CSV (`record_ref`, `group_id`) comes next: a group of n records expands to n(n−1)/2 pairs, members are de-duplicated, and a large expansion is flagged. |
| **Vendor validation** | An unknown reference is an error listing the affected rows and blocks the run. The user must confirm the export is complete, with the omitted-pair assumption explained. |
| **Field roles** | full name, first name, last name, email, phone, date of birth, address, city, postcode, country, other. Jev receives the mapped fields the user selects (default: all), with original values. |
| **Blocking** | Rules = one field or a composite (AND); rules combine with OR; exact equality on normalized values. Email: trim and lowercase. Phone: E.164 using the evaluation's country. Name: trim, lowercase, collapse spaces. Postcode: trim, uppercase, remove spaces. A missing or unparseable value gets no key. Presets: Email, Phone, Name, Name + postcode. |
| **Limits** (in `limits.ts`) | 500 records, 3 vendors, 5,000 unique pairs, a warning above 50 records per bucket (showing its pair count), 1 MB files. Checked before any Jev call; an over-limit plan is blocked with a per-rule and per-vendor breakdown; vendor pairs are never dropped. |
| **Identity definition** | Two text areas, "Counts as the same individual" and "Does not count", prefilled with editable defaults. They map directly onto Jev's `criteria.true` and `criteria.false`. The request's `state` holds only the two records' fields and the country: no references, vendor names or scores. |
| **Threshold** | A decision is a match when `noul ≥ threshold`. Users can change it on the results page, with an explanation. The default comes from the Milestone 1 test (0.5 until then). Scores within a band around the threshold get a "low confidence" flag, a filter rather than a category. |
| **Sign-in** | Email and password against local Supabase (confirmations are off locally), handled in server actions through the existing auth-only client. Live evaluations require login. |
| **Ownership** | `requireUser()` in every action and page; all queries are scoped by `ownerId`; the demo evaluation is read-only through a dedicated reader, and mutations reject it. Tested with two users. |
| **UI conventions** | Tokens and existing `ui/` components; add Select, Checkbox, Progress and Tabs only when a screen uses them; next-intl strings; filters in URL params; TanStack Query for the run loop. |
