**Where the code limits it:**
- `src/server/pairsight/splink/score-dataset.ts:139` skips the job when the evaluation's type isn't `person`, and records the reason as `not_people`.
- The scoring model in `services/splink/pairsight_splink/model.py` is built only for people. It compares first name, surname, date of birth, postcode, email and phone. It also narrows the search for people only: same-sounding surname plus birth year, same-sounding first name plus postcode area, or exactly the same postcode.

**What organisations and products get instead:**
- They start with their type's default comparison rules (the hand-written TypeScript ones), so the plan is never empty.
- People evaluations with fewer than 200 records also get the default rules, because the model needs enough records to learn from.
- If the scoring isn't set up or fails, the plan falls back to the default rules too, and says so.

The roadmap (`docs/PairSight-Scale-Roadmap.md`, item 6) leaves removing the TypeScript rules for later, "organisations and products still do" need them.

**What it would take to extend this:** a separate model for each type, since organisations need comparisons like company name, registration number and address, and products need things like SKU and description. Each new model would be benchmarked first, as the Splink service rule requires.

No, it doesn't keep learning. It learns afresh from each file, then forgets.

**What happens on each upload:** when a records file is saved, Splink trains a new model on that file alone. With no labels, it works out how often real duplicates and unrelated records agree on each field: name, email, company number, barcode and so on. It then scores the pairs and stores the results for that dataset. A 2,000-person file therefore gets weights fitted to that file's own patterns. In one file a shared surname means little, because everyone's a Smith; in another it means more.

**What doesn't happen:**
- **Nothing carries over between files or customers.** No model is saved; each dataset starts from the same starting point.
- **It doesn't learn from Jev's answers.** Jev judges every suggested pair, but those verdicts never go back into Splink. The roadmap lists that as "left for later" (item 6): Jev's answers could sharpen the next run's suggestions.
- **The same file always gives the same pairs.** Training is seeded, which keeps runs reproducible and lets earlier Jev scores be reused.

**What we tuned is fixed code:** the comparisons per type, the fields with fixed weights (company number, barcode, size, colour), the 5% floor, and the fallback when nothing anchors the estimate. All of it lives in `services/splink/` and only changes when we change it and rerun the benchmark.

If you'd like it to improve over time, the natural next step is feeding Jev's verdicts back in as labels, either per evaluation (a second run gets sharper) or pooled across evaluations of the same type. That's a separate piece of work.
